## Message Flow

Lobster's dispatcher is a stateless main loop: it blocks in `wait_for_messages()`, processes
whatever arrived, and calls `wait_for_messages()` again. All durable state lives in the
filesystem (message files) and SQLite (claims, sessions) — never in the dispatcher's own
memory — so the dispatcher can be killed and restarted at any point with no loss of in-flight
work.

### Directory states

Every message is a JSON file that moves between four directories under `~/messages/`:

```
inbox/  --mark_processing()-->  processing/  --mark_processed()-->  processed/
  ^                                  |
  |                                  v
  '-------- retry (backoff) ---- failed/  (mark_failed(), permanent after max_retries)
  ^
  |
  '---- stale-processing recovery (age > timeout, claim released first)
```

- **`inbox/`** — newly arrived messages, not yet claimed by anyone.
- **`processing/`** — claimed messages, currently being handled by the dispatcher.
- **`processed/`** — terminal success state; archived, never touched again.
- **`failed/`** — messages that errored; either waiting for a scheduled retry
  (`_retry_at` timestamp) or permanently failed (`_permanently_failed: true` after
  `max_retries`, default 3, backoff 60s/120s/240s).

### The atomic claim gate

Filesystem `rename()` alone is not a safe claim primitive under concurrent callers. Lobster
layers a SQLite claim gate (`src/mcp/claims.py`) in front of the filesystem move:

- `message_claims` table: `INSERT OR FAIL` on `message_id` (`TEXT PRIMARY KEY`). One caller's
  insert commits; any other concurrent caller gets an integrity error and is told
  `already_claimed`. The filesystem rename to `processing/` only happens *after* the claim is
  won — the claim, not the rename, is the arbiter.
- `dispatcher_lock` table: a single-row lock (`id = 1` via `CHECK` constraint) recording which
  HTTP session currently owns the dispatcher role. `wait_for_messages()` takes or replaces this
  lock on every call (`force_replace_dispatcher_lock`), so a second concurrent dispatcher loop
  cannot run alongside the first — if the previous lock holder's session is no longer live, the
  new caller takes over silently; if it looks live, a warning is logged but the takeover still
  proceeds (fail-open, since a wedged dispatcher is worse than a brief double-lock).

Both tables live in the same `agent_sessions.db` file as the session store described below —
there is no separate claims database.

### `wait_for_messages()` mechanics

`handle_wait_for_messages` (`src/mcp/inbox_server.py`) does the following, in order, on every
call:

1. Tags the calling HTTP session as the dispatcher session (tag-on-first-use: whichever
   session calls `wait_for_messages` first is definitionally the dispatcher).
2. Takes/refreshes the SQLite dispatcher lock (see above).
3. Writes heartbeat and "WFM-active" signal files that the external health check
   (`scripts/health-check-v3.sh`) uses to distinguish "blocked in a healthy wait" from
   "actually frozen." A background daemon thread keeps refreshing these on wall-clock time so
   they don't go stale during long streaming calls that block the asyncio event loop.
4. Recovers stale `processing/` messages back to `inbox/` (`_recover_stale_processing`; releases
   the SQLite claim first so a fresh claim can be won) using a type-aware timeout — 90s for
   text, 300s for media where transcription/download is slow.
5. Recovers retry-eligible `failed/` messages back to `inbox/` (`_recover_retryable_messages`)
   once their `_retry_at` backoff has elapsed.
6. Drains "reconciler ghost" `subagent_result` messages generated by the startup sweep for
   sessions already known to be dead, so a batch of dead-session notices doesn't flood the
   dispatcher on every restart.
7. Starts a filesystem watcher (`watchdog.Observer`) on `inbox/` *before* doing the initial glob
   check, closing the TOCTOU window where a message could arrive between the glob and the
   watcher starting.
8. Blocks until a message arrives or `timeout` (default 72000s / 20h) elapses, then returns
   through `check_inbox()`, prefixed with a compact "active sessions" summary block so the
   dispatcher always knows what background agents are in flight without a separate query.

### Claiming and finishing a message

- `mark_processing(message_id)` — wins the SQLite claim, then moves `inbox/` → `processing/`.
  Also does message-type validation against the known taxonomy, queues a background
  "observation" for the user model, and conditionally injects user-model context into the tool
  response.
- `claim_and_ack(message_id, ack_text, chat_id, ...)` — the preferred pattern for anything
  taking longer than a few seconds. Combines the claim step and an acknowledgement `send_reply`
  into one atomic call, so there's no window where a message is claimed but the user has not
  yet been told work is underway. If the claim fails, no ack is sent; if the ack fails after a
  successful claim, the message simply stays in `processing/` and stale recovery handles it.
- `mark_processed(message_id)` — moves `processing/` (or `inbox/` as a fallback) → `processed/`,
  updates the claim row's status, archives any accidental duplicate files sharing the same
  `message_id` (issue #2039), and persists the message to `messages.db` if that write path is
  enabled.
- `mark_failed(message_id, error, max_retries)` — moves the message to `failed/`, writes
  `_retry_count`/`_last_error`/`_retry_at` retry metadata, and releases the SQLite claim so the
  message is re-claimable on the next retry attempt. Once `_retry_count > max_retries`, the
  message is marked `_permanently_failed` and stays in `failed/`.

### Dispatcher vs. subagent roles

- The **dispatcher** is whichever session called `wait_for_messages()` — the only tool that is
  dispatcher-exclusive. Everything the dispatcher does that would take more than about 7 seconds
  is delegated to a background subagent (the "7-second rule"); the dispatcher's only steady-state
  job is claim → delegate/reply → `mark_processed` → `wait_for_messages()` again.
- **Subagents** are spawned via the `Agent`/`Task` tool with a `task_id`/`chat_id` in their
  prompt frontmatter. They never call `wait_for_messages`. They report back via `write_result`
  (and, for user-facing tasks, `send_reply` directly first, for crash-safe delivery — see
  `.claude/sys.subagent.bootup.md`).

For the full pseudocode, startup sequence, and behavioral rules governing the dispatcher loop,
see `.claude/sys.dispatcher.bootup.md`. For the subagent-side contract (`write_result`,
`write_observation`, delivery patterns), see `.claude/sys.subagent.bootup.md`.

## Session Store Design and Lifecycle

Background agent sessions (subagents spawned via `Task`) are tracked in a SQLite database —
`src/agents/session_store.py` — which replaced an earlier `pending-agents.json` file approach.

**DB location:** `~/messages/config/agent_sessions.db` (resolved from `LOBSTER_MESSAGES`, WAL
mode, `synchronous=NORMAL`). The same file also hosts the `reports` table (`/report` command
records) and the claim/lock tables described above — one database for all cross-process
coordination state, rather than several small files.

### Schema (`agent_sessions` table)

Key columns: `id` (PK), `task_id`, `agent_type`, `description`, `chat_id`, `source`, `status`,
`output_file`, `timeout_minutes`, `spawned_at`, `completed_at`, `last_seen_at`, `notified_at`,
`trigger_message_id` / `trigger_snippet` (causality — which inbox message caused this spawn),
`reply_message_ids`, `stop_reason`, `idempotency` (`safe` | `unsafe` | `unknown` — whether an
interrupted task is safe to auto-re-run), and `task_origin` (`user` | `scheduled` | `internal`).
New columns are added via idempotent `ALTER TABLE ... ADD COLUMN` migrations wrapped in
try/except, run every time `init_db()` is called — safe on both fresh installs and existing
databases.

### Status lifecycle

```
 (spawn)
   |
   v
"starting"  --(PostToolUse hook: auto-register-agent.py registers immediately)
   |
   v
"running"   --(session_start(), called by the dispatcher / agent itself once initialised)
   |
   +---> "completed"  (session_end(status="completed"), normal write_result path)
   +---> "dead"       (session_end(status="dead"), reconciler/startup sweep decided it's gone)
   +---> "failed"     (session_end(status="failed"))
```

- `"starting"` exists because the `auto-register-agent.py` PostToolUse hook registers a session
  the moment the `Task`/`Agent` tool call is observed — before the spawned agent has read its
  own bootup context or called anything itself. This closes a gap where a session that died
  before fully initializing would never appear in the store at all.
- `session_end()` matches rows by *either* `id` **or** `task_id`, and updates rows in *either*
  `"running"` **or** `"starting"` — so a session that never progressed past `"starting"` (e.g. it
  crashed immediately) can still be closed out cleanly.

### Reconciliation (`cleanup_stale_running_sessions`)

Run at MCP server startup, this function decides the fate of every row still marked `running`/
`starting` from before the restart. Critically, it does **not** assume that a restart of the MCP
server means the agent is dead — Claude Code background agents are independent OS processes, not
children of the MCP server, and can outlive an MCP restart. The rules, evaluated per row:

1. `output_file` set, target JSONL missing on disk → **dead**, but only after a 2-minute grace
   period (the symlink may not exist yet for agents spawned seconds before the restart).
2. `output_file` set, last `stop_reason` in the file is `"end_turn"` → **completed**.
3. `output_file` set, last `stop_reason` is `"tool_use"` or absent → **left running** (the agent
   may still be alive; the normal reconciler loop times it out later if needed).
4. No `output_file`, elapsed time since `spawned_at` exceeds `timeout_minutes` (default 120m) →
   **dead** (fallback heuristic for sessions that never got an output file registered).
5. No `output_file`, elapsed time within timeout → **left running**.

An explicit exclusion (`COALESCE(agent_type, '') != 'dispatcher'`) keeps the dispatcher's own
session — which legitimately has no `output_file` — from ever being reconciled or re-notified as
a dead subagent (issue #781). This is the kind of bug this document exists to prevent recurring;
see `docs/engineering-lessons-learned.md` for the general pattern of dispatcher-vs-subagent
detection bugs.

### Other lifecycle-adjacent writes

- `set_trigger()` — records which inbox message caused a spawn (causality trail for debugging).
- `set_notified()` / `get_unnotified_completed()` — tracks whether the user has been told about
  a completed/dead session yet, so a crash between completion and notification doesn't silently
  drop the result; the startup sweep re-sends anything unnotified within `since_hours`.
- `append_reply_message_id()` — appends to a JSON array of outbound message IDs sent about this
  session, for audit/debugging.
- `get_active_sessions()` / `get_session_history()` / `find_session()` — pure read queries used
  by `get_active_sessions` (MCP tool) and the `wait_for_messages` active-sessions prefix.

## MCP Servers

Lobster's `install.sh` registers exactly one MCP server with Claude Code:

### `lobster-inbox` (primary, always registered)

- **Transport:** Streamable HTTP (`claude mcp add --transport http lobster-inbox -s user <url>`),
  not stdio — this decouples the MCP server's process lifetime from any single Claude Code
  process, so restarting Claude Code does not require restarting the MCP server (and vice
  versa).
- **Implementation:** `src/mcp/inbox_server.py`.
- **Responsibilities** (see `README.md` "MCP Tools" section for the full tool list):
  - Message queue: `wait_for_messages`, `check_inbox`, `send_reply`, `mark_processing`,
    `mark_processed`, `mark_failed`, `claim_and_ack`, `list_sources`, `get_stats`.
  - Subagent result bus: `write_result`, `write_observation`.
  - Agent session tracking: `register_agent`/`session_start`, `get_active_sessions`,
    `get_session_history`.
  - Task management: `create_task`, `update_task`, `list_tasks`, `get_task`, `delete_task`.
  - Scheduled jobs: `create_scheduled_job`, `list_scheduled_jobs`, `get_scheduled_job`,
    `update_scheduled_job`, `delete_scheduled_job`, `check_task_outputs`, `write_task_output`.
  - Skill system: `get_skill_context`, `list_skills`, `activate_skill`, `deactivate_skill`,
    `get_skill_preferences`, `set_skill_preference`.
  - IFTTT behavioral rules: `list_rules`, `add_rule`, `get_rule`, `update_rule`, `delete_rule`.
  - Voice transcription: `transcribe_audio` (local whisper.cpp, no cloud API).
  - `/report` records: `create_report`, `list_reports` (SQLite-backed, same DB as sessions).

### `lobster-inbox` (read-only HTTP variant, optional)

- **Implementation:** `src/mcp/inbox_server_http.py`.
- Exposes a **read-only** subset (tasks, memory, conversation history) over HTTP so a *remote*
  Claude Code instance (e.g. a laptop) can read Lobster's context without being able to send
  messages, mark things processed, or otherwise act on the owner's behalf. Bearer-token
  authenticated (`MCP_HTTP_TOKEN`). This is a separate process/port from the primary server, not
  a mode flag on it.

### Companion HTTP servers (not MCP servers)

Three other processes live under `src/mcp/` but do **not** speak the MCP protocol and are not
registered with `claude mcp add` — they're plain HTTP services that support adjacent Lobster
features:

- `wire_server.py` — serves agent session data (SSE + polling) to the `lobster-watcher`
  frontend dashboard.
- `observability_server.py` — exposes a `/observability` JSON endpoint with uptime, token
  cost estimates, and a recent-events timeline.
- `bot_talk_mirror.py` — mirrors inter-Lobster ("bot-talk") messages to the EventBus and routes
  inbound cross-Lobster messages into `~/messages/inbox/` with `source="bot-talk"`; not a server
  process itself, but a module invoked from the message pipeline.

### Historical note: GitHub MCP was removed

Earlier Lobster versions registered a `github` MCP server. It was removed in favor of the `gh`
CLI for all GitHub operations (`scripts/upgrade.sh` migration 31 strips any leftover
`mcpServers.github` entry from Claude Code settings). Both `.claude/sys.subagent.bootup.md` and
`README.md` now document `gh` as the only supported path for GitHub work — do not reintroduce
an MCP-based GitHub integration without updating this document.

### Machine-local extras (not part of the Lobster repo)

A running Lobster instance's `~/.claude.json` may list additional `mcpServers` entries (for
example `kissinger` or `activepieces`) installed via the Lobster skill/shop system
(`lobster-shop/`). These are optional, user-installed extensions layered on top of the core
system described above, not part of what `install.sh` sets up by default. This document
describes the core system only.

## Subagent Model-Tier Strategy

Lobster assigns each subagent an explicit model in its `.claude/agents/*.md` frontmatter, rather
than letting the dispatcher choose a model per call. The stated tiers
(`.claude/sys.subagent.bootup.md`, mirrored in `CLAUDE.md`):

| Tier | Model | Use For | Relative cost |
|------|-------|---------|------|
| **High** | `opus` | Complex coding, architecture, debugging | 1x (baseline) |
| **Standard** | `sonnet` | Planning, research, execution, synthesis | 0.6x |
| **Light** | `haiku` | Verification, plan-checking, integration checks | 0.2x |

The documented rationale: reserve the most expensive model for tasks where deep reasoning
failures are costly (shipping broken code, misdiagnosing a bug), use the mid tier for the bulk
of structured work, and push cheap, narrow pass/fail judgment calls (does this plan look right?
does this integration check pass?) down to the cheapest tier.

**`general-purpose` / `lobster-generalist`** is documented as inheriting from the
`CLAUDE_CODE_SUBAGENT_MODEL` environment variable rather than being pinned to a specific tier in
the table — it's the escape hatch for open-ended background work that doesn't map to a
specialized agent.

**When to override:** if a task normally handled by a `sonnet`-tier agent needs unusually deep
reasoning (e.g. a complex multi-system execution plan), the documented escalation path is to use
`functional-engineer` (`opus`) instead of inventing a one-off model override.

### Drift between the documented table and actual agent frontmatter

The tier table above (and its source in `CLAUDE.md` / `sys.subagent.bootup.md`) references a
family of `gsd-*` agents (`gsd-executor`, `gsd-planner`, `gsd-phase-researcher`,
`gsd-codebase-mapper`, `gsd-research-synthesizer`, `gsd-roadmapper`, `gsd-project-researcher`,
`gsd-verifier`, `gsd-plan-checker`, `gsd-integration-checker`) plus `gsd-debugger`. **None of
these files exist under `.claude/agents/` in the repository today** (verified: `.claude/agents/`
contains only `brain-dumps.md`, `compact-catchup.md`, `functional-engineer.md`,
`lobster-auditor.md`, `lobster-generalist.md`, `lobster-ops.md`, `nightly-consolidation.md`,
`review.md`, `session-note-appender.md`, `session-note-polish.md`). Actual `model:` frontmatter
found in those files:

| Agent | `model:` frontmatter |
|---|---|
| `functional-engineer.md` | `opus` (matches the table) |
| `review.md` | `opus` (not mentioned in the table) |
| `lobster-generalist.md` | `claude-opus-4-6` (full model ID, not the `sonnet` the "inherit" row implies) |
| `brain-dumps.md` | `sonnet` |
| `compact-catchup.md` | `sonnet` |
| `nightly-consolidation.md` | `sonnet` |
| `session-note-polish.md` | `sonnet` |
| `lobster-auditor.md` | `claude-sonnet-4-6` (full model ID) |
| `lobster-ops.md` | `haiku` |
| `session-note-appender.md` | `haiku` |

This is flagged here rather than silently fixed — reconciling the table with reality (deciding
whether the `gsd-*` family was retired, renamed, or never merged, and whether
`lobster-generalist` pinning to opus is intentional) is a product/process decision out of scope
for this documentation slice. See the PR description for this file for a pointer to that
follow-up.

For the authoritative, machine-checkable answer to "what model does agent X actually run,"
always check that agent's own frontmatter under `.claude/agents/<name>.md` — treat the table
above as intent, not ground truth.
